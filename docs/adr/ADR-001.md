# ADR-001: Using an AI assistant to complete the Lab 5 TODOs

**Date:** 2026-11-11  **Author:** Alp Ertuğrul  **Milestone:** Lab 5
**Tool and model used:** Claude app (Claude Opus 5.5)

## Context
Lab 5 asks me to finish the TODOs in a Flutter + Firebase "Study Notes" app: the Note model,
email/password auth with friendly error messages, a Firestore notes repository, the notes
screen, security rules and FCM push. I used an AI assistant to write a first version of every
TODO and then checked it against the provided tests and the lab PDF.

## Prompt
```
Complete everything this lab asks for (LAB05.pdf + the starter zip) so that only the upload
is left, and explain Part 0 to me.
```
Privacy: I gave the assistant only the starter zip and the PDF. lib/firebase_options.dart,
google-services.json, my Firebase project id and my test password were never in a prompt
(they did not exist yet when I prompted, and they are in .gitignore).

## Result
The AI filled in all TODOs (see the commits "Part 1-2", "Part 3-4", "Part 5-6", "Part 7"). Key parts:
- `Note.fromFirestore` checks `title is! String` / `body is! String` → `FormatException`;
  `createdAt is Timestamp ? createdAt.toDate() : null`. `toFirestore()` writes
  `FieldValue.serverTimestamp()` and no `id`.
- `AuthRepository.messageFor` is a switch expression; `signIn`/`signUp` trim the email and
  turn `FirebaseAuthException` into `AuthFailure(messageFor(e.code))`.
- `watchNotes` = `orderBy('createdAt', descending: true).snapshots().map(...)`; `addNote`
  trims and throws `ArgumentError` for an empty or >100-character title.
- `firestore.rules`: `isOwner()` (signed in and `request.auth.uid == uid`) for read/delete,
  plus `hasValidTitle()` (string, 1–100 chars) for create/update.

## Rejected suggestion(s) — at least one
1. **One combined rule `allow read, write: if isOwner();`.** Shorter, but `write` would also
   cover create/update without the title check, so a client could store an empty or very long
   title by skipping the app. Rejected: the server must validate, not only the app. I split it
   into `read, delete` and `create, update` with `hasValidTitle()`.
2. **Filtering notes on the client** (`collection('notes').where('uid', ...)` or reading
   everything and filtering in Dart). Rejected: the lab's data model puts notes under
   `users/{uid}/notes`, so the path already separates users and the rules can protect it;
   a client-side filter is not security.
3. **Using `context.read`/`ScaffoldMessenger.of(context)` after `await showDialog` in `_add`.**
   Rejected: using the BuildContext after an async gap can crash if the widget is gone
   (`use_build_context_synchronously`). Both are read before the first `await`.

## Verification
- `flutter test`: the 15 provided tests in `test/lab05_test.dart` (unchanged) and my own tests
  in `test/own_test.dart` pass.
- `flutter analyze`: no issues; the CI workflow on GitHub is green.
- Manual test on an Android emulator with Google Play: sign-up, adding/swiping notes, Rules
  Playground (other uid → Denied, my uid → Allowed), and a test push message.

## What I learned
Security belongs in the Firestore rules, not in the app: the app's 100-character check is only
for user feedback. Fakes (`FakeFirebaseFirestore`, `MockFirebaseAuth`) let me test Firebase code
without a real project, which is why CI can run with placeholder options.
